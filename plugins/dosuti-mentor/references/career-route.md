# Карьерный маршрут — 0.4.24, этап7B

Диалог организует [plan-career](../skills/plan-career/SKILL.md). Модель строит
маршрут; CLI проверяет структуру, зависимости и сохранённые основания. Нет
автоматического поиска, генератора учебной программы или оценки готовности к найму.

```sh
PYTHON PLUGIN_ROOT/scripts/course.py career-route --course COURSE --profile USER --session CHAT
PYTHON PLUGIN_ROOT/scripts/course.py career-route --course COURSE --profile USER --session CHAT --route-file JSON --expected-revision N --reason 'Почему предлагается маршрут'
```

N — текущая revision intent. Перед предложением требуется сохранённая цель; её
описывает пользователь, либо она явно предварительная. Настоящие цели и ответы
не заменяются тестовым карьерным сценарием.

route-file содержит точные поля summary,sample_id,learner_context,steps.
- summary: краткое описание предложения.
- sample_id: ID сохранённой выборки илиnull для маршрута без рыночных утверждений.
- learner_context: self_report,available_time,timeframe (строка илиnull), unknowns
  (0–50 строк). Это данные беседы/явные неизвестные, не оценки и не анкета за ученика.
- steps:1–50 объектов с полями id,title,rationale,kind,requirements,prerequisites,units.
  title до1000 символов, rationale до4000. kind=foundation|market|project|review.
  prerequisites — уникальные ID уже предшествующих шагов. Циклы и ссылки вперёд
  запрещены. Порядок нужно объяснить, наличие CLI-проверки не доказывает его качество.
  units —0–20 уникальных ID подготовленных тем. Их актуальные хеши закрепляются.
  requirements — ID требований выборки только для market; у остальных шагов[].

market требует хотя бы одно требование с текущей required/preferred-поддержкой
без classification_conflicts. Нулевой текущий спрос, архив/unknown/программы сами
по себе не поддерживают рыночный шаг. Другие шаги можно предложить без sample_id,
с явным фундаментальным/проектным обоснованием. Один работодатель не равен рынку.

Пока выборка связана целиком по content_sha256. Даже изменение её заголовка требует
пересмотра привязанного маршрута; это консервативное поведение. Изменение связанной
unit/предпосылки, research review или самой цели тоже отражается в needs_review.
Дата выборки и freshness показаны отдельно. С0.4.26 шаги kind=market требуют
повторной ручной сверки наблюдений через30 дней; старый рыночный маршрут получает
needs_review, новый/принятие старого блокируются до сверки. Основания foundation,
project, review без рыночных шагов этим возрастным правилом не блокируются.
Порог — эвристика; даже недавний снимок не доказывает актуальную доступность.
Роль/регион/уровень сопоставляет модель по смыслу, не строковым равенством CLI.

## Хранение и согласование

career-route записывает обычное предложение intent с дополнительным career-контекстом
в **один атомарный файл**, отдельного второго журнала маршрута нет. Блокировки:
общая .study-units.lock, затем профильная learning-intent.lock; изменение выборки/
тем согласовано с предложением и принятием. CAS защищает от конкурирующих чатов.

История v1 читается без изменений. Первая запись карьерной метаинформации переводит
заголовок intent в learning_intent_v2, сохраняя события. Дальнейшие обычные изменения
остаются v2. Для чтения такого профиля нужен плагин0.4.24 или новее. Лимит intent
64MiB логического журнала; после900000 байт используется document_parts_v1
(см. learning-intent.md). Старые части сохраняются, чтение полной истории остаётся.

В предложение попадают sample_id+sample_sha256, сведения беседы и шаги с единицами
id+sha256. Метаданные и названия обычных plan.steps должны совпадать. Принятие
остаётся отдельным intent-событием по learning-intent.md:

```json
{"accept_proposal":true}
```

Прими после реального согласия с показанным предложением. Структурный CLI не
доказывает согласие человека. Устаревшие основания не позволяют принять предложение;
прежний принятый план не заменяется сам. Новое предложение тоже не заменяет старый
план до принятия. Пересмотр оставляет все цели/предложения/принятия в истории.

## Чтение и прогресс

career-route возвращает intent, а для карьерных plan/proposal — статус оснований,
причины пересмотра, дату выборки, learner_context и steps. В progress — критерии
связанных units текущего профиля и all_criteria_demonstrated, stale,
evidence_time_valid,later_verified_criteria. Нет процентов или автоматических новых
оценок. Повреждённый журнал даёт progress_valid=false, а не выдуманное незнание.
У другого профиля свои цель/маршрут/оценки. Реестр тем и выборки общие внутри курса.

Старый intent/read/status/context тоже видит needs_review карьерного плана; задача
занятия помечается для сверки, если её принятый план требует пересмотра. Это не
запрет учиться и не потеря результатов. Выбор следующей темы пока делает модель
по принятому маршруту и фактическим ответам, не автоматическая очередь-планировщик.
