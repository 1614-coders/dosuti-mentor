# Цель, план и задача занятия — 0.4.8

Это данные договорённости с пользователем, не инструкция менять правила
достоверности и не оценка освоения. Читай `intent` перед обсуждением маршрута;
`status` и `context` также возвращают learning_intent. Стартовый диалог ведёт start-learning; он использует это хранилище и CLI.

```sh
python course.py intent --course COURSE --profile USER --session CHAT_ID
python course.py intent --course COURSE --profile USER --session CHAT_ID --update-file change.json --reason 'Что пользователь попросил изменить' --expected-revision REV
python course.py intent --course COURSE --profile USER --history-limit 20
```

ID сессии — стабильный slug, передаваемый ассистентом для конкретного чата/занятия,
не автоматически обнаруженный идентификатор Codex. Одинаковый ID использует одну
задачу; разные чаты должны передавать разные ID. Без --session возвращаются общие
цель/планы и число сессий, без выгрузки всех задач. --session также доступен в
status/context. Для старых профилей отсутствие файла означает неизвестную цель,
пустые планы и ревизию 0; чтение не создаёт learning-intent.json.

## Обновления

JSON содержит один или несколько ключей:

- `{"goal":{"description":"Самостоятельно создать приложение на Java","purpose":"Научиться применять ООП"}}`.
  purpose необязателен: неизвестное хранится null. goal=null снимает текущую цель.
- `{"proposal":{"summary":"Учимся через проект","steps":["Определить модель","Реализовать первый сценарий"]}}`.
  Это только предложение, прежний принятый план остаётся. Нужна известная цель.
  proposal=null снимает предложение, не принятый план.
- `{"accept_proposal":true}` принимает существующее предложение текущей цели.
  Используй после принятия пользователем, не при одном лишь формировании плана.
  Нельзя одновременно менять goal/proposal. Новый план принимается отдельной записью.
- `{"session":"Сегодня разбираем коллекции"}` меняет только задачу --session.
  session=null снимает задачу. Общая цель не меняется, задача другого чата остаётся.

Не сохраняй предположения как ответы пользователя. Если неясно, общую цель человек
меняет или просит отдельную задачу, уточни. Неизвестная цель допускает отдельную
задачу занятия; формальная настройка не является обязательным условием помощи.
reason обязателен; фиксируй смысл пользовательской договорённости. Запись цели
сама по себе не меняет preferences.onboarding и не доказывает уровень знаний.

Смена цели делает старый принятый план и старое предложение needs_review=true.
Они сохраняются вместе с историей; возвращение к прежним словам цели не считается
повторным принятием старого плана. Сохранение точно той же цели не сбрасывает план.
У задачи сохраняются ревизии цели и принятого актуального плана. Изменение цели
или принятие нового плана отмечает старую задачу needs_review, но не удаляет её.
Новая задача после смены цели не привязывается к уже устаревшему плану.

## Учебный контекст со слов пользователя

Если ответ нужен для маршрута, сохраняй только явно сообщённый текст:

```json
{"learning_context":{"context":"Прохожу курс Java, затрудняюсь с коллекциями","constraints":"Два вечера в неделю","self_assessment":"Считаю, что понимаю циклы"}}
```

Все три поля необязательны; обновление содержит хотя бы одно из них.
Новая запись меняет только переданные поля, `null` явно снимает выбранное поле;
предыдущее значение остаётся в истории. `intent` возвращает `learning_context`
как объект: отсутствующее поле означает неизвестное, а не нулевой уровень.
Самооценка — слова пользователя, не verified assessment, evidence или прогресс.
Эта запись не меняет preferences, onboarding, unit_learning или course.progress.
Подача/формат проверок остаются в существующих preferences без дублирования здесь.
Не сохраняй предположения, пропуск и «не знаю» как ответы; при пропуске не вызывай
обновление. Смена цели сохраняет контекст и историю; проверь его применимость
перед новым предложением маршрута. Новый proposal не означает принятие.

Первая запись `learning_context` переводит журнал в `learning_intent_v3`, сохраняя
все события v1/v2. Последующие записи сохраняют v3, в том числе при карьерном
предложении. Старые v1/v2 читаются с пустым контекстом без записи и обязательной
миграции; старым версиям плагина чтение нового v3 не обещается. Общая ревизия,
блокировка и expected-revision защищают контекст вместе с целью/планом.

## Хранение и совместимость

Журнал learners/USER/learning-intent.json принадлежит профилю внутри курса,
общий для его чатов. Разные курсы и пользователи независимы. --profiles-dir
по-прежнему разделяет только личные предпочтения: цели туда не переносятся.
Данные вне пакета плагина; перенос курса сохраняет их, абсолютных путей в журнале нет.

Запись атомарная, под блокировкой, с обязательным expected-revision. При конфликте
перечитай intent и согласуй изменение вместо перезаписи. История содержит
последовательные ревизии, причину, время и изменения; текущий вид восстанавливается
из неё. По умолчанию история в ответ не выгружается, --history-limit допускает 0–100.
Повреждённый/неизвестный журнал возвращает valid=false и не перезаписывается;
сначала сохрани копию и восстанови его явно. Обычные файлы/папки обязательны,
символические и жёсткие ссылки на журнал отвергаются.

Ограничения: до50 шагов в предложении,200 ID сессий,64MiB логической истории.
С0.4.26 после900000 байт журнал сохраняется как document_parts_v1 с SHA256-частями
в learning-intent-objects рядом с JSON. Чтение проверяет все части и восстанавливает
журнал в памяти; неизменённые старые v1/v2 читаются без записи. Внутренние события,
ревизии целей/планов и задач сохраняются. Старый плагин манифест не читает.
При переносе/резервировании нужна вся папка профиля, не один JSON. Старые части
автоматически не удаляются; физический объём может превышать логический.
При достижении нового лимита запись отклоняется без обрезания. Сохрани весь курс перед явным архивированием. Журнал не даёт
криптографической гарантии подлинности договорённости; ассистент записывает её
по реальному диалогу. Изменения целей не удаляют события знаний и домашки.


## Карьерные предложения с0.4.24

Дополнительный proposal.career создаётся через career-route по
[career-route.md](career-route.md). Включает источники и структурированные шаги;
обычные steps совпадают с их названиями. Первая запись метаданных переводит журнал
в learning_intent_v2 с сохранением прежних событий. v1 остаётся читаемым; старым
плагинам новый заголовок не обещается. Принятие отдельно через accept_proposal;
перед ним проверяются цель и актуальность оснований. Изменение источников/тем
помечает план и связанную задачу занятия needs_review, не стирая результаты.

С0.4.34 UTF-8 частей декодируется постепенно с переносом незавершённых символов.
Проверяются размеры/хеши каждой части и общий SHA256, JSON разбирается только
после проверки полного документа. Промежуточные текстовые части освобождаются
перед разбором; формат/ревизии/семантические хеши не меняются. Это сокращение
лишних буферов, не потоковая выборка отдельных записей: полный текст и результат
всё ещё находятся в памяти, операции остаются пропорциональны размеру документа.

## Проверяемые основания шага

Общий план остаётся в intent. Необязательный `proposal.step_bases` содержит по одному
объекту на каждый элемент `steps`, в том же порядке. Каждый объект ссылается хотя бы
на одно основание; можно сочетать поля:

```json
{"proposal":{"summary":"Карты и практика","steps":["Разобрать карты","Решить задачу"],"step_bases":[{"unit_ids":["maps"],"diagnostic_event_revisions":[3]},{"prerequisites":[1]}]}}
```

`prerequisites` — номера предыдущих шагов этого предложения, начиная с 1;
`unit_ids` — существующие подготовленные units курса, без stale источников;
`diagnostic_event_revisions` — ревизии реальных событий answer текущего профиля
в diagnostic-learning.json. Это не ревизия вопроса, accept или самооценки. Основание
может содержать confirmed, needs_practice или unknown: оно объясняет выбор шага,
не доказывает освоение. `basis_status.diagnostic_evidence` показывает процитированные
ответы с вопросом и оценкой. Проверки не определяют педагогическую достаточность.

Диагностика необязательна: отсутствие/отказ не блокируют предложение без ссылок на
диагностику. При недостатке данных явно назови неизвестное и предварительность.
Карьерные основания остаются в существующем `proposal.career`; career-route принимает
необязательный `step_bases` в карточке маршрута и передаёт его в intent.

`route_state` различает preliminary (обычное предложение без структурированных
оснований), proposed (предложение со step_bases или career) и accepted (принятый план).
Это состояние договорённости, не уровень знаний; предложенный маршрут может оставаться
предварительным по содержанию. Старые предложения читаются и принимаются по прежнему
контракту без обязательной диагностики или миграции. Явное согласие пользователя
по-прежнему требуется ассистенту для отдельного accept_proposal.

При записи предложения и принятии повторно проверяются ссылки и актуальность.
Чтение возвращает `basis_status` и needs_review, не исправляет маршрут. Смена цели
отмечает прежнее предложение/план needs_review и запрещает его принятие до нового
предложения; ответы и история сохраняются. `study-next` возвращает эти данные через
learning_intent только для обсуждения ближайшего шага, не принимает и не перестраивает
план автоматически.

Первая запись step_bases переводит журнал в learning_intent_v4, сохраняя события
v1/v2/v3 и учебный контекст. Последующие записи сохраняют v4; старые заголовки
не могут объявлять это поле. Новый формат старым плагинам не обещается.

## Единый учебный прогресс — 0.4.65

`learning_progress` — read-only представление уже существующих журналов. Его
возвращают `intent`, `status`, `resume`, `learn-unit` и `study-next`; запись
старого `progress` также выводит эту сводку после сохранения события. Нового
файла, миграции и автоматического изменения маршрута нет.

В нём есть `studied_units`, `demonstrated_units`, `unit_gaps`, результат
диагностики, `completed_steps`, `current_step`/`next_step` и `stopped_at` для
продолжения (с0.4.67 см. ниже). `demonstrated_units` означает все критерии текущей
версии unit с сохранённой независимой проверкой и допустимым временем, не
долгосрочное mastery.

Для шага с `diagnostic_event_revisions` сводка читает фактическую оценку ответа,
а не только номер события. `unknown` даёт `address_identified_gap`,
`needs_practice` — `practice_partially_confirmed`, `confirmed` —
`confirm_transfer`. Это объясняет выбор ассистента; он не пропускает
предпосылки, не создаёт unit и не принимает маршрут за пользователя.

## История и продолжение — 0.4.67

История и результаты собираются независимо от наличия плана и его `needs_review`.
Последний блок отключает только предложения старого маршрута: `next_step` и
`current_step` остаются null. Для legacy-шагов без targets `completed_steps`
сохраняет прежний смысл завершённых unit-заданий; для targets с0.4.74 используй
`criterion_completed_steps`, без зачёта компетенции по review модели.
`blocked_steps` отдельно показывает невыполненные зависимости и их цепочки.
Шаг без unit не считается завершённым автоматически.

`studied_lessons` показывает последние lesson-статусы, `confirmed_lesson_knowledge`
и `completed_lesson_tasks` — сохранённые проверки/практику. Их verification равен
`legacy_recorded_claim`: старый SQLite не содержит доказательств уровня unit.
`explained` в подтверждения не входит; устаревшая домашка остаётся историей и
не считается действующим успехом. Unit-попытки отделены от объяснений; исторические
успешные задания в `completed_unit_tasks` имеют признак актуальности версии `current`.
Это не утверждение об отсутствии более поздних ошибок.

`lesson_history` и `unit_history` содержат последние 100 событий с общим счётчиком
и флагом `*_history_truncated`; исходная полная история не обрезается. Успешные
unit-задания также ограничены последними 100, общий счётчик — `completed_unit_task_count`.

`continuations` перечисляет сохранённые точки. У unit есть session и актуальность;
старый lesson-курсор один на профиль (`scope=shared_profile`, session=null), его
нельзя приписывать конкретному чату. Недействительные точки остаются видны для
сверки. `stopped_at` заполняется лишь при одной действующей точке. При нескольких
`continuation_choice_required=true`: предложи выбор, не выбирай по времени или
номеру ревизии. `resume --session CHAT` сохраняет прежний контракт lesson-курсора
и добавляет ту же общую сводку.

Чтение SQLite использует mode=ro, без создания файла и миграции схемы. Для WAL
оно блокируется с явной причиной: даже read-only SQLite может менять shared memory.
Сводка unit при этом доступна, но общий valid=false; автоматического checkpoint нет.

С0.4.68 чтение legacy-курсора независимо от SQLite. Даже при ошибке WAL действующий
cursor.json остаётся в continuations вместе с unit-checkpoints. Несколько
действующих точек требуют выбора. При valid=false stopped_at всегда null,
даже если видна лишь одна действующая точка: неполные данные не дают основания
выбрать её автоматически. Повреждённый cursor.json сообщает отдельную причину,
не скрывая корректные lesson/unit-данные и предшествующую SQLite-ошибку.

## Учебные цели шага и адаптация — 0.4.69

В существующем step_bases необязательный targets связывает компетенцию с
проверяемым результатом конкретной версии unit. Пример одного основания:

```json
{"unit_ids":["maps"],"diagnostic_event_revisions":[3],"targets":[{"competence":"Объяснить замену значения map","rationale":"В ответе перепутаны уникальность ключа и значения; нужна самостоятельная трассировка","unit_id":"maps","unit_sha256":"SHA256_АКТУАЛЬНОЙ_UNIT","criteria":[1],"diagnostic_event_revisions":[3]}]}
```

Все поля target обязательны; diagnostic_event_revisions может быть пустым,
если диагностики нет. Компетенция в процитированном ответе должна точно совпадать
с competence. Unit обязана входить в unit_ids шага; критерии — существующие
1-based номера её версии, sha256 берётся из реального чтения unit. Диагностические
ссылки target — подмножество ссылок шага. Rationale объясняет педагогическую связь;
CLI не проверяет её смысл и не доказывает, что выбранная тема подходит компетенции.
Если тема неподходящая, исправь предложение, а не переименовывай пробел для валидации.

С 0.4.74 шаг с targets не получает автоматического подтверждения компетенции:
даже supported alignment_review — суждение модели, не независимая проверка.
Выполненные критерии отдельно отражаются в criterion_completed_steps, не в
completed_steps. Остальные критерии unit это не подтверждает.
Объяснение/помощь/непроверенные критерии не дают выполнения задания.
Повторение по сроку не стирает результат, но создаёт рекомендацию новой проверки.

study-next.roadmap возвращает steps с компетенциями, rationale, фактическими
состояниями критериев, ревизиями/временем evidence и историческими диагностическими
оценками; recommendations используют ту же политику adaptive_learning. Outcome
criteria_demonstrated относится к независимым unit-ответам, не переписывает диагностику
и не означает подтверждения компетенции target. competence_status=unverified.
uncovered_diagnostic_gaps сохраняет диагностические пробелы: ссылка на учебную
цель и успех по её unit сами по себе не являются их независимой проверкой.
Такие пробелы и шаги без targets дают review_route, не автоматическую вставку тем.
Legacy_unmapped означает старый план без новых связей: помогай по прежним данным,
при необходимости предложи обоснованный пересмотр, не объявляй курс непригодным.

Ошибки/помощь ведут к review_error/fresh_independent_task; explained — к
check_understanding; отсутствие ответа — initial_check; наступившее повторение —
recheck_due. После подтверждения целевых критериев доступен следующий шаг без
невыполненных зависимостей. Решения skip/defer подавляют предложения по прежним
правилам. При needs_review нет учебных предложений старого маршрута, только
review_route; неполные данные дают status=incomplete. Общая очередь recommendations
study-next остаётся для отдельных тем, а roadmap учитывает принятую структуру.

Изменения порядка/содержания сохраняй только отдельным proposal. Покажи человеку,
что меняется, почему и по каким ответам. Не заменяй принятый plan до явного согласия.
Для целевого пересмотра передавай adaptation_basis из свежего study-next.roadmap:

```json
{"base_plan_revision":4,"diagnostic_revision":8,"unit_learning_revision":12}
```

Три ревизии относятся к фактически прочитанным журналам, числа примера не копируй.
Для первого предложения с targets снимок заполняется при записи, если не указан.
Для пересмотра существующего плана с targets снимок обязателен. При сохранении и
принятии проверяются текущие ревизии под существующими locks. Любая запись unit,
включая checkpoint другого чата, консервативно требует перепроверить предложение.
Не обновляй снимок старого предложения механически: перечитай ответы и реши,
сохранилось ли обоснование. После принятия новые ответы сами не делают plan
неактуальным; рекомендации пересчитываются по фактическим результатам.

Первая запись targets/adaptation_basis переводит learning-intent.json в v5,
сохраняя все события v1–v4. Чтение старых журналов не меняет их; новые поля не
допускаются под старым заголовком. Нового хранилища компетенций/оценок нет.

## Содержательная проверка связи — 0.4.70

Target может содержать alignment_review. Отсутствующий review старых v5 читается
как unreviewed: он не стирает plan, unit-ответы и изученные темы, но больше не
даёт завершение шага/покрытие диагностического пробела. Автоматической миграции нет.
Для новой связи прочитай полный unit с источниками и исходный диагностический
вопрос/ответ; не считай название или техническую ссылку доказательством смысла.

```json
{"alignment_review":{"verdict":"supported","competence":"Объяснить замену значения map","diagnostic_event_revisions":[3],"diagnostic_reason":"Ученик считает, что повторный ключ создаёт вторую запись; проверяем замену значения и размер map.","criterion_links":[{"criterion":1,"criterion_text":"Объяснить замену существующего ключа и размер map","source":1,"quote":"put replaces the value associated with an existing key","explanation":"Самостоятельная трассировка двух put с одним ключом проверяет именно различие замены и вставки."}]}}
```

verdict: supported/unsupported/uncertain. diagnostic_reason объясняет связь с
наблюдаемым ответом; без диагностики — с целью, без выдуманных результатов.
С 0.4.71 новые reviews обязаны содержать competence и diagnostic_event_revisions:
точную компетенцию и тот же набор ответов, что у target (пустой без диагностики).
Несовпадение, частичная привязка и bool вместо номера отклоняются. Перенос review
Map в target synchronized запрещён; не переписывай эти поля механически, заново
проверь содержание. Старые v6 без обоих полей читаются как unreviewed без записи.
criterion_links обязателен как список; supported требует ровно одну запись на
каждый целевой критерий. criterion_text должен дословно совпадать с критерием,
source — 1-based индекс источника unit, quote — непустая дословная цитата из
полных строк содержимого выбранного источника (для видео — из речи),
explanation — содержательное объяснение предлагаемой связи.
Проверяются версии unit, критерии и происхождение цитат. Аннотации/название/notes
не считаются текстом источника. Поддержаны текстовые источники и речь video;
для материала только на картинке или project timeline сначала подготовь отдельный
текстовый источник. Не придумывай цитату ради положительного review.

Контрпроверка ассистента: можно ли успешно выполнить критерий, совсем не понимая
компетенцию? Если да, verdict должен быть unsupported, при недостаточных материалах
— uncertain. Пример: задача о HashMap.put не проверяет synchronized/happens-before.
Одного supported, общего rationale или совпадения названия недостаточно.
CLI не умеет доказывать семантическую истинность explanation: неверно составленный
полный review всё ещё может пройти структурные проверки. Ответственность за этот
разбор остаётся у ассистента; не выдавай его за независимый автоматический вывод.

study-next.roadmap.steps[*].targets[*] содержит alignment, alignment_review и
outcome=alignment_unverified при отсутствии целостного положительного review. Тогда критерии
unit всё равно видны, а вместо практики по неподтверждённой связи даётся review_route.
Даже supported targets не подтверждают компетенции и не закрывают пробелы. Отрицательный review
можно сохранить в предложении как причину пересмотра, он не подтверждает освоение.
Обновление review — обычный proposal с актуальным adaptation_basis и явным принятием.
Первый review переводит существующий журнал в v6 с сохранением предыдущих событий;
следующие записи сохраняют v6. Под заголовками v1–v5 новые reviews запрещены.

## Неполная сводка при ошибке intent — 0.4.73

Если learning-intent.json повреждён или его схема не поддерживается, intent
возвращает valid=false и причину, но читает независимые lesson/unit-результаты и
курсор в learning_progress. У этой сводки valid=false, route_state=unknown,
stopped_at=null; current_step/next_step не выбираются. История не считается пустой
только из-за невозможности прочитать маршрут. Причины других ошибок дополняются.
study-next также возвращает valid=false и пустую очередь recommendations,
roadmap.status=incomplete. Доступные факты не являются разрешением выбрать маршрут.
learn-unit, resume и status могут показать эту неполную сводку без KeyError.
Ошибка не чинит и не заменяет файл; запись intent блокируется до восстановления.

## Граница доверия к модели и совместимость сводки — 0.4.74

verdict=supported, competence/revisions, rationale и explanation вводятся тем же
ассистентом. Они не могут быть независимым подтверждением его собственного
содержательного вывода. Поэтому target_alignment возвращает status=unverified,
review_verdict=supported, evidence_valid=true при корректных ссылках и цитатах.
evidence_valid — только целостность свидетельств, не семантическая истинность.
Не добавлено ни классификатора по словам, ни порога длины, ни фиктивного «второго
доверенного» флага. Автоматического пути к verified competence в этой сводке нет.

quote должна совпадать с целыми последовательными строками выбранного источника
или полным однострочным ASR-фрагментом. Проверка использует границы строк, а не
длину и не пунктуацию: короткая строка кода x++; допустима как цитата, подстрока put
в предложении о HashMap — нет. Если сам источник состоит из одного слова, его
цитата остаётся лишь целостной цитатой, а не доказательством компетенции.

Старые v6 с обрезанными цитатами не переписываются: plan получает needs_review,
unit-ответы остаются доступны. Новый proposal с такой цитатой отклоняется.

Для targets completed_steps не заполняется по model-review. Новое вычисляемое
criterion_completed_steps содержит индексы шагов с независимо выполненными
указанными критериями и целостным proposed review. Зависимости, current_step и
next_step используют выполнение заданий, чтобы не заставлять повторять решённое.
Они не доказывают знание предпосылок или обобщённой компетенции. В roadmap.steps
отдельно видны completed и criteria_completed; outcomes criteria_demonstrated
и competence_status=unverified не взаимозаменяемы. Legacy-планы без targets
сохраняют completed_steps по прежним unit-результатам, не как доказательство
семантики произвольного названия шага.

Схемы v1–v6 и события не меняются: новой миграции/хранилища нет. Меняется контракт
вычисляемого ответа. Клиенту 0.4.74 следует читать criterion_completed_steps для
результатов задач и не использовать completed_steps как обобщённую оценку знаний.
Обновляй bundled scripts и skills совместно. Принятый план не заменяется, диагностика
не переписывается, CAS и проверка устаревшего предложения сохраняются.
